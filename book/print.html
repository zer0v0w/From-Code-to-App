Building Mobile Apps with Dart & Flutter

Building Mobile Apps with Dart & Flutter

A beginner-first, project-driven path from writing your first line of code to building and presenting a working mobile application.

This book is designed for students with little or no programming experience. It combines small programming experiments, guided explanation, visual interface building, real data, and independent projects.

The central idea is simple: touch the code, observe what it does, understand why, then build something with it.

This is a living teaching material. Verify examples against the current stable Dart and Flutter documentation before each cohort.

Foreword

This bootcamp is not meant to make students memorize a list of Dart keywords or Flutter widgets. It is designed to help them become comfortable enough with code to experiment, read errors, make changes, and build a small application without a tutor dictating every line.

The course deliberately introduces concepts when students have a reason to use them. It alternates between small, safe experiments and visible outcomes, then revisits the same ideas in more realistic projects.

The instructor’s role is not to prevent every mistake. It is to make mistakes safe, observable, and useful.

Introduction

Who this book is for

This book assumes no previous programming experience. Students may have encountered computer science terminology in university, but they should not need to know how to write a program, understand object-oriented programming, or use Flutter before beginning.

The journey

  1. Learn to change and reason about code.
  2. Use Dart to express data, decisions, repetition, and reusable logic.
  3. learn how Flutter turns Dart code into a user interface.
  4. Build screens, forms, and navigation.
  5. Connect the UI to remote data and authentication.
  6. Complete a guided project, then prepare and present an independent one.

What students should be able to do at the end

Students should be able to explain the main files in a small Flutter application, modify and debug Dart code, build multiple screens from a design, handle basic user input, fetch and display remote data, use Supabase Auth and database access with appropriate policies, run basic checks, and publish their source code to GitHub.

This is an introductory outcome, not a claim of production-level expertise. Advanced architecture, large-scale state management, store publishing, and native platform integration remain next steps.

How the material is organized

The book uses the Rust Book’s broad information architecture:

  • Concept pages explain one idea through small examples.
  • Project pages guide students through an outcome that requires several ideas together.
  • Appendices provide cheat sheets, checklists, and links for later review.

Not every lesson has exactly the same shape. A page about null safety should not read like a project walkthrough, and a project should not read like a dictionary of widgets.

Before You Begin

Instructor preparation

Do not spend the first two hours installing tools. Before the first session, ask students to complete a setup check and provide a fallback for anyone whose device is not ready.

  • Install Flutter using the official installation guide.
  • Run flutter doctor and resolve the required issues for the chosen target.
  • Install/configure an editor with Dart and Flutter support.
  • Create and run a sample Flutter project on an emulator, simulator, desktop, or physical device.
  • Confirm that hot reload works in debug mode.
  • Install Git and verify git --version.
  • Provide a known-good starter repository or archive in case individual setup fails.

Do not require every platform

For a beginner bootcamp, choose one supported target for the teaching environment. Android emulator/physical Android is a practical default for a mobile-focused course; adapt to the cohort’s hardware and the instructor’s setup. iOS builds require macOS and Xcode.

Pre-course checklist

A student is ready when they can:

  • Open the starter project.
  • Run the app and see it on a device/emulator.
  • Change a visible string and see it update after hot reload.
  • Find the terminal and the lib/ directory.
  • Send the instructor a screenshot or short message confirming successful setup.

If setup fails

Pair the student with the prepared device or starter environment. Do not make environment troubleshooting the hidden prerequisite for learning programming. Record unresolved setup issues and handle them outside the core lesson where possible.

Official resources: Install Flutter, Flutter learning pathway, Hot reload.

How to Use This Book

The recurring teaching rhythm

Use this as a default, not a rigid formula:

  1. Question or problem: give students a reason to care.
  2. Mental model: explain the idea in plain language.
  3. Worked example: run something small and concrete.
  4. Prediction: ask what will happen before running it.
  5. Change: let students modify one thing.
  6. Feedback: show what happened, including failures.
  7. Application: give a related task without step-by-step instructions.
  8. Retrieval: ask students to explain or recreate the key idea without looking.

A presentation is a support for this experience, not a transcript of the instructor. Put the code, diagram, output, rule, and necessary labels on screen. Put the longer explanation in the instructor’s spoken explanation and in the written lesson around the example.

A suggested 120-minute session rhythm

  • 0–10 min: opening problem and recall of the previous session.
  • 10–25 min: first concept and worked example.
  • 25–40 min: predict/change/run.
  • 40–55 min: second concept or variation.
  • 55–60 min: short break / reset.
  • 60–80 min: guided exercise.
  • 80–100 min: independent attempt or debugging.
  • 100–112 min: feedback and common mistakes.
  • 112–120 min: retrieval check and next-session teaser.

Adjust the rhythm to the actual cohort. Students who cannot yet solve the small task should not be rushed into a new abstraction merely to finish the slide deck.

Three rules for the instructor

  • Do not introduce syntax that students must use before you have shown what problem it solves.
  • Do not treat a successful run as proof of understanding: ask students to predict, modify, and explain.
  • Do not correct every error immediately. Ask what the error says, where it happens, and what they expected first.

Chapter 1: First Contact with Programming and Dart

The goal is comfort, not completeness. Students should become willing to change code, run it, inspect the result, and recover from mistakes. Dart is the language from the beginning so the transition to Flutter does not require learning a second syntax.

Teaching principle

Keep returning to the same activity: predict → change → run → explain. Early code should be small enough that the student can understand all of it at once. The first assignment is not meant to be impressive; it is meant to show that the student can use the basics independently.

Readiness check

Before moving to Flutter, each student should be able to:

  • Write a short Dart program with variables, conditions, loops, a function, and a collection.
  • Explain the difference between changing a value and changing the code’s logic.
  • Find and fix at least one syntax or logic error.
  • Explain what a nullable value means at a basic level.
  • Create and use a simple class, even with notes available.

If many students cannot do these things, reduce the Chapter 1 assignment rather than pushing forward because the calendar says so.

1.1 First Contact with Code

Code is a set of instructions and values that a computer evaluates; a small edit can change the program’s behavior.

Session length: 120 minutes. Prerequisites: environment is already prepared. Main outcome: students can read a tiny Dart program, change data, run it, and describe what changed.

Learning outcomes

Students can identify a variable, a value, a basic type, a program output, and the difference between changing data and changing a program’s instructions.

Suggested teaching flow

1. Start with a visible change (0–10 min)

Show one tiny program. Ask students to predict the output before you run it.

void main() {
  var fruit = 'apple';
  print(fruit);
}

Change 'apple' to 'orange' and run again. Do not begin with a long definition. Let them notice the cause-and-effect relationship first.

2. Explain the smallest mental model (10–30 min)

  • A value is a piece of data, such as 'apple', 7, or true.
  • A variable is a named place/reference through which the program works with a value.
  • A type describes the kind of value, such as String, int, double, or bool.
  • print() sends text to the console/output area.
  • main() is where a Dart command-line program begins.

Show these examples and ask what type each value has:

String fruit = 'apple';
int quantity = 3;
double price = 2.5;
bool isAvailable = true;

Then compare an explicit type with inference:

var name = 'Mira'; // Dart infers String.

Keep the details light. The aim is to recognize the concepts, not memorize every declaration rule.

3. Input and output (30–45 min)

Explain the general idea:

  • Input: information supplied to a program.
  • Processing: the program works with the information.
  • Output: information the program produces.

Use editable variables as the first kind of input, then show one real console-input example on the instructor’s machine:

import 'dart:io';

void main() {
  stdout.write('Enter your name: ');
  final name = stdin.readLineSync();
  print('Hello, $name!');
}

Explain only the flow: prompt → keyboard input → value stored → output. readLineSync() can return a nullable value; do not teach the full null-safety rules here. This example needs a command-line environment and may not work in every browser sandbox. Explain that real apps receive input through different interfaces, such as a text field or button.

4. Guided sandbox experiments (45–70 min)

Ask students to make one edit at a time:

  1. Rename fruit to snack everywhere.
  2. Change 'apple' to 'orange'.
  3. Change quantity from 3 to 10.
  4. Change the type of a value, then observe what breaks if the assigned value is incompatible.
  5. Introduce a typo deliberately and read the error.

After each edit, ask: What do you expect to happen, and why?

5. The prepared Flutter bridge (70–90 min)

Use a starter Flutter app whose widget tree is already written and hidden from the lesson. The student-editable part is a Dart value that the starter displays:

var fruit = 'apple';
// The prepared UI displays the value of `fruit`.

Students change apple to orange, save, and use hot reload. Explain only that the running app reflects the value; do not teach the widget tree yet. This is a prepared bridge, not a separate Dart file automatically connected to a Flutter process.

6. Mini challenge (90–110 min)

Students create a small “snack receipt” that stores an item name, quantity, and price, then prints a readable line of output. Provide the first example, but ask them to change the data and sentence themselves.

7. Retrieval (110–120 min)

Without looking, students explain:

  • What is the variable name in var fruit = 'apple';?
  • What is the value?
  • What does print() do?
  • What changed when the value changed? What would happen if the variable name changed but one use was not updated?

Common beginner mistakes

  • Treating quotes as part of the text value rather than Dart syntax.
  • Changing a variable’s name in one place but not in its other uses.
  • Confusing = (assignment) with == (comparison); reserve full comparison coverage for Session 3.
  • Assuming every error means they are “bad at coding.” Use errors as feedback.

Further reading

  • Dart: Hello World and variables
  • Dart variables
  • Flutter hot reload

1.2 Operations and the Calculator

A program can transform inputs into outputs; a function gives a useful operation a name.

Main outcome: students can trace an arithmetic expression, change an operator, and call a simple function with arguments.

Teaching flow

1. Start with the calculator (0–10 min)

Show a tiny calculator with two values and one operation. Begin with addition, then ask what a single symbol change might do.

void main() {
  final first = 8;
  final second = 2;
  print(first + second);
}

Explore +, -, *, /, and % with small values. Show one example of parentheses changing evaluation order. Do not turn this into a math lecture.

2. Make the operation visible (10–30 min)

Ask students to predict results for expressions before executing them. Cover arithmetic versus comparison operators at a basic level, but leave conditions for the next lesson.

print(8 + 2); // 10
print(8 * 2); // 16
print(8 % 3); // 2

3. Introduce a function only as needed (30–50 min)

A function is a named, reusable operation. Parameters are its inputs; return gives a result back to the caller.

int sum(int a, int b) {
  return a + b;
}

void main() {
  print(sum(8, 2));
}

Trace the values of a and b on the board. Distinguish returning a value from printing a value.

4. The modification challenge (50–75 min)

Give students a function that calculates a sum. Ask them to change its behavior to calculate a power instead. Provide the import and unfamiliar library call as scaffolding so the lesson stays focused on changing behavior rather than library research:

import 'dart:math' as math;

num calculate(int base, int exponent) {
  return math.pow(base, exponent);
}

Let them first rename the function and then test calculate(2, 3). Restrict the exercise to non-negative integer exponents for now. Later, when loops are understood, students can implement a simple power function themselves.

5. Calculator extension (75–105 min)

Students modify a provided calculator by changing the operation, adding a new operation, or changing the values. If the class is progressing well, let them make the operation a parameter rather than duplicating code.

6. Retrieval (105–120 min)

Ask students to describe the flow: arguments → parameters → calculation → return value → output.

Common mistakes

  • Thinking return and print mean the same thing.
  • Forgetting that a function call executes the function.
  • Confusing a parameter (the name in the function declaration) with an argument (the value passed into the call).
  • Modifying several things at once and losing track of which change caused the result.

Further reading

  • Dart functions
  • Dart math library

1.3 Decisions and Loops

Conditions let a program choose; loops let it repeat.

Main outcome: students can read and modify simple branches and loops, and predict their behavior before running them.

1. Decisions

Start with a practical question: “If the score is at least 50, should the result say Pass or Try again?” Introduce bool, comparison operators, and if / else together.

void main() {
  final score = 72;

  if (score >= 50) {
    print('Pass');
  } else {
    print('Try again');
  }
}

Cover >, <, >=, <=, ==, !=, &&, ||, and ! through prediction puzzles, not a slide of symbols alone.

2. Repetition

Start with repeated print() calls, ask what is wasteful, then replace them with a loop.

for (var number = 1; number <= 5; number++) {
  print(number);
}

Teach the three parts of the counting loop only after students can explain the outcome. Then introduce a for-in loop over a provided list, and use while only if time permits.

3. Playful challenges

  • Change a score so the branch takes a different path.
  • Predict which of two conditions will be true.
  • Make a countdown from 5 to 1.
  • Print only even numbers from 1 through 10.
  • Modify a loop boundary and explain the off-by-one difference.
  • Make a small “guess the number” program with a fixed guess before adding interactive input.

4. Debugging checkpoint

Give students a short program with one intentional bug: a wrong comparison, a loop boundary that repeats one extra time, or an assignment where a comparison is intended. Ask them to predict the wrong behavior, locate the line, change one thing, and run it again.

This is a small first debugging task. The larger homework comes after they have used collections in the next lesson.

Common mistakes

  • Confusing = with ==.
  • Writing a loop that never changes its condition.
  • Assuming code inside an if block always runs.
  • Miscounting loop iterations.

Review

  1. What type of value does a condition need to produce?
  2. What changes between one loop iteration and the next?
  3. Predict the output of a loop with a starting value of 1 and an upper bound of 3.
  4. Describe the steps you used to fix the debugging task.

Further reading

  • Dart control flow
  • Dart loops

1.4 Collections, Problem Solving, and Debugging

A collection lets a program work with many related values instead of one value at a time.

Main outcome: students can use a List and a Map, loop through values, call a function, and debug a small program made from familiar parts.

1. Lists

Use an everyday theme such as a list of foods, tasks, or student scores.

void main() {
  final fruits = ['apple', 'orange', 'banana'];
  print(fruits[0]);
  print(fruits.length);

  for (final fruit in fruits) {
    print(fruit);
  }
}

Explain that a list is ordered and index-based, and that the first index is 0. Demonstrate adding an item with add() and accessing a value by index. Explain that final prevents reassignment of the list variable but does not automatically make the list’s contents immutable; keep this nuance brief.

2. Maps

Use a map to associate keys with values:

final student = {
  'name': 'Lina',
  'score': 87,
};

print(student['name']);
print(student['score']);

Describe it as key → value lookup. Avoid introducing type parameters deeply at first; return to <String, int> when students are ready to inspect types.

3. Functions with collections

Give students a function that receives a list and prints each item. Then let them modify it to count items, sum scores, or search for a value.

int total(List<int> scores) {
  var result = 0;
  for (final score in scores) {
    result += score;
  }
  return result;
}

The aim is to combine concepts they already know, not to introduce five new collection methods in one go.

4. Basic problem-solving routine

Teach students to make a tiny plan before writing code:

  1. Restate the problem in plain language.
  2. Identify the input and expected output.
  3. Work one example by hand.
  4. Break the problem into small steps.
  5. Write a small amount of code.
  6. Run it with a normal case and an edge case.
  7. Explain why it works.

5. Debugging homework

Give students a short list/map program containing two or three bugs. The bugs should be within concepts already taught: wrong index, incorrect loop condition, incorrect key, or a function returning the wrong result.

Ask them to submit:

  • The corrected code.
  • The observed error or wrong output.
  • A short explanation of each fix.
  • One test input they added themselves.

Common mistakes

  • Using an index that is outside the list’s range.
  • Assuming a map key exists.
  • Modifying a collection and then forgetting that its contents changed.
  • Writing code before deciding what output should be produced.

Review

  • When is a list a better fit than a map?
  • Why does the first list index equal zero?
  • What does a function return when it reaches return result;?
  • What makes a debugging explanation better than just pasting corrected code?

Further reading

  • Dart collections
  • Dart lists
  • Dart maps

1.5 Dart Fundamentals, Null Safety, and OOP

Dart adds rules that help make code clearer and safer; classes let related data and behavior live together.

Important pacing note: this is a dense session. In the first hour, prioritize final/const, late at a basic level, functions, and null safety. In the second hour, teach only the basics of classes and objects. Do not add inheritance or advanced OOP unless the cohort is moving unusually quickly.

Part A — Dart language details (about 60 minutes)

var, final, and const

var nickname = 'Ali'; // The variable can be reassigned.
final startedAt = DateTime.now(); // Assigned once.
const maxLives = 3; // A compile-time constant.

For beginners, use this simple explanation: var lets Dart infer the type; final means the variable is assigned once; const means the value is a compile-time constant. Avoid saying that a final object is always deeply immutable.

late

Explain that late delays initialization of a non-nullable variable until later. Show it for recognition and explain the risk: reading it before assigning a value causes a runtime error. Prefer normal initialization unless there is a clear reason to use late.

Functions in more depth

Revisit parameters, return values, and named parameters, because Flutter constructors use named parameters heavily.

String greet({required String name, String greeting = 'Hello'}) {
  return '$greeting, $name!';
}

Introduce string interpolation ('$name') and explain required as a requirement at the call site.

Null safety

A nullable value may be absent. Dart’s type system makes this possibility explicit.

String name = 'Rana';
String? nickname = null; // Can be a String or null.

print(nickname ?? 'No nickname');

Teach these symbols through actual examples:

  • String?: this value may be null.
  • value != null: check before using the value.
  • ??: use a fallback when the left side is null.
  • ?.: access a member only if the value is not null.
  • !: assert non-null; use carefully, because it can fail at runtime.

Do not overwhelm students with flow analysis rules. The essential lesson is to represent optional data honestly instead of pretending it must exist.

Part B — Classes and objects (about 60 minutes)

Start with a familiar thing that has data and actions: a Task with a title, a completion flag, and a method to mark it complete.

class Task {
  Task(this.title) : isDone = false;

  final String title;
  bool isDone;

  void complete() {
    isDone = true;
  }
}

void main() {
  final task = Task('Review variables');
  task.complete();
  print(task.isDone); // true
}

Explain:

  • A class describes a kind of object.
  • An object/instance is created from the class.
  • A field stores data.
  • A constructor sets up a new object.
  • A method is a function associated with the object.

Avoid deep theory about inheritance, interfaces, polymorphism, or design patterns here. Students need enough class knowledge to understand models and Flutter widget classes later.

Checkpoint

Students modify Task to add a priority or owner, then explain which values may be null and which are guaranteed to exist.

1.6 Revision, Collections Tricks, and Async

Consolidation is part of learning: students retrieve and combine ideas rather than only encountering new ones.

Main outcome: students can combine core Dart concepts and explain what Future, async, and await mean at a beginner level.

Part A — Revision through a single program

Begin with a small program that tracks a list of tasks or scores. Ask students to identify and explain the variables, types, condition, loop, collection, function, and class. Then ask them to change the behavior before you add new content.

Review useful collection operations only when they solve a visible problem:

  • add() to append.
  • length to count.
  • contains() to test membership.
  • where() to filter a list.
  • map() to transform values (clarify that this is the list transformation method, not the Map key/value collection type).
  • for-in to process items one by one.

Do not teach list operations as a disconnected vocabulary list. Compare a loop to a where() or map() example and explain why the method is useful.

Part B — Async as a preview, not a deep dive

A synchronous line finishes before the program moves to the next line. Some operations, such as network requests, take time. Dart represents a future result with a Future.

Future<String> loadMessage() async {
  await Future.delayed(const Duration(seconds: 1));
  return 'Ready';
}

Explain only:

  • Future<String> means the string will be available later (or an error will occur).
  • async marks a function that uses asynchronous syntax.
  • await waits for the future’s result without blocking the app’s event loop.

Do not turn this into a lecture about isolates, streams, or the event loop. Students will use async/await practically when they fetch data in Chapter 4.

Short exercise

Students call a provided asynchronous function and display its result in a CLI example. They should explain the difference between receiving a Future and receiving the value from that future.

Chapter 1 readiness check

Students should now be able to complete the CLI project without copying the entire solution. Notes are allowed. Search and documentation are tools, not cheating; the assessment is whether they can connect the pieces and explain their code.

Further reading

  • Dart asynchronous programming
  • Dart concurrency
  • Dart lists and collections

Chapter Project: A Tiny CLI Game

Goal

Build a small command-line game or string-manipulation program that proves the student can use the Chapter 1 fundamentals. Do not require async or Flutter in this assignment.

Suggested project options

Option A — Number/choice guessing game

The instructor provides a simple fixed secret value at first. Students ask for a guess, compare it, provide feedback, and allow a limited number of attempts. If command-line input is available, students can read a guess from the terminal; otherwise, use a provided list of guesses to focus on core logic first.

Option B — Word/phrase utility

Ask for or define a phrase and then count characters, count words, reverse text, check whether a word is present, or normalize the phrase. Choose only two or three operations; do not turn the assignment into a library of unrelated features.

Option C — Score tracker

Store a list of scores, calculate a total/average, identify a pass/fail result, and print a summary.

Requirements

  • Use variables with sensible types.
  • Use at least one function with parameters and a return value.
  • Use a condition.
  • Use a loop or iterate over a collection.
  • Use a list or map where appropriate.
  • Handle at least one likely invalid or edge case.
  • Include comments only where they clarify a decision.
  • Explain one bug encountered and how it was fixed.

What not to require

  • Flutter UI.
  • Async/await.
  • Inheritance or advanced OOP.
  • External packages.
  • A polished graphic interface.

Appendix A: Dart Cheat Sheet

Values and variables

var name = 'Mira';          // inferred String
String city = 'Nablus';     // explicit type
int count = 3;
double price = 2.5;
bool isReady = true;
final createdAt = DateTime.now();
const maxItems = 10;
  • var: infer a type; the variable may be reassigned to another value of the same type.
  • final: assign once.
  • const: compile-time constant.
  • late: promise that a non-nullable variable will be initialized before use; avoid unless necessary.

Strings

final greeting = 'Hello, $name';
final summary = '${count * price} total';

Conditions and loops

if (count > 0) {
  print('Has items');
} else {
  print('Empty');
}

for (var i = 0; i < 3; i++) {
  print(i);
}

for (final item in items) {
  print(item);
}

Functions

int add(int a, int b) => a + b;

String greet({required String name}) {
  return 'Hello, $name';
}

Collections

final names = <String>['Mira', 'Omar'];
final scores = <String, int>{'Mira': 91, 'Omar': 86};

names.add('Lina');
print(names.length);
print(scores['Mira']);

List is an ordered sequence. Map associates keys with values. Remember that looking up a missing key can produce null.

Null safety

String? optionalName = null;
final displayName = optionalName ?? 'Guest';

if (optionalName != null) {
  print(optionalName.length);
}
  • T?: value may be null.
  • ??: fallback if the left side is null.
  • ?.: access only when non-null.
  • !: assert non-null; can fail at runtime.

Classes

class Task {
  Task(this.title);
  final String title;
  bool isDone = false;
}

Async

Future<String> loadLabel() async {
  await Future.delayed(const Duration(milliseconds: 300));
  return 'Done';
}

Use the official Dart language tour for full syntax and details.

Appendix C: Debugging Guide

Debugging is a repeatable process, not random editing.

The loop

  1. Reproduce: what exact action produces the problem?
  2. Observe: what did you expect, and what happened instead?
  3. Read: inspect the first useful error message and the relevant line/stack trace.
  4. Classify: syntax/compile-time, runtime, or logic/behavior error?
  5. Hypothesize: state one reason the issue might happen.
  6. Change one thing: avoid changing five lines at once.
  7. Run again: did the evidence support the hypothesis?
  8. Record: explain the cause and fix in one or two sentences.

Error categories

  • Syntax/analyzer error: code does not follow language/API rules or types do not match.
  • Runtime error: the program runs but fails during execution, such as an invalid list index or a forced null assertion.
  • Logic error: the program runs but produces the wrong result.
  • UI/layout error: the app builds, but something is clipped, overflowing, misaligned, or absent.
  • Network/backend error: request, credentials, permissions, or response handling failed.

Flutter debugging checklist

  • Did I read the first meaningful error, not only the last line?
  • Is the widget actually in the returned tree?
  • Did I change state inside setState where appropriate?
  • Is a network call accidentally running inside build()?
  • Is a ListView/Expanded receiving valid layout constraints?
  • Does the asset path exist and appear in pubspec.yaml?
  • Is the server response successful and the JSON key correct?
  • Could the value be null?
  • Is a backend policy denying access intentionally?

Tooling

Introduce DevTools gradually: log/console first, then source-level debugger and widget/layout inspection when useful. Do not try to teach the entire DevTools suite in one session.

Appendix D: App Quality Checklist

Use this before a project demo or GitHub submission.

Functionality

  • The app launches on the agreed target.
  • Main buttons and navigation work.
  • Invalid form input receives useful feedback.
  • Empty, loading, success, and error states are handled where relevant.
  • Repeated taps do not create confusing duplicate actions.

UI and accessibility

  • Text hierarchy is clear.
  • Text remains usable with larger system font settings.
  • Buttons are easy to tap.
  • Important information is not communicated by color alone.
  • Images have suitable sizing; important images have semantic descriptions where appropriate.
  • The screen is checked on a narrower layout or second device size.
  • Content can scroll without overflow.

Code and maintainability

  • Names describe the purpose of values/functions/widgets.
  • Repeated UI is extracted when it meaningfully reduces duplication.
  • build() describes UI and does not initiate repeated API requests.
  • Models, services, and UI responsibilities are reasonably separated.
  • At least one meaningful behavior has been tested manually or with a small automated test.

Data and security

  • Network failures and invalid responses do not crash the main flow.
  • Null/optional values are handled intentionally.
  • Supabase policies match the intended access.
  • No password, token, private key, or service-role key is committed.
  • Sample/demo data does not expose a real person’s private information.

Repository

  • Project source and run instructions are in GitHub.
  • README states purpose, features, prerequisites, setup, and run commands.
  • Screenshots show the current app.
  • Known limitations are stated honestly.

Appendix F: Glossary

  • API: an interface that lets one program request functionality or data from another.
  • Argument: a value supplied when calling a function.
  • Authentication: checking who a user is.
  • Authorization: deciding what an authenticated identity may do.
  • Backend: the server-side systems and services an app communicates with.
  • Build method: in Flutter, the method that describes the widget subtree for the current inputs/state.
  • Class: a definition that describes the data and behavior of a kind of object.
  • Collection: a structure that stores multiple values, such as a list or map.
  • Constructor: code used to create and initialize an object.
  • Dart: the programming language used by Flutter.
  • Debugging: locating and correcting the cause of unexpected behavior.
  • Function: a reusable unit of code that can take inputs and produce a result or effect.
  • Future: Dart’s representation of a value or error that becomes available later.
  • JSON: a text format commonly used to exchange structured data.
  • Model: a Dart representation of data used by the application.
  • Null safety: Dart’s type-system features that make optional/missing values explicit.
  • Parameter: a named input slot declared by a function.
  • Repository: a boundary that represents a source of application data; introduced only at a beginner level here.
  • RLS (Row Level Security): database policies that control which rows a request may access or modify.
  • Service: code that communicates with an external system, such as an HTTP API.
  • State: values that can change while an application runs and affect what it displays or does.
  • Widget: an immutable description/configuration of a piece of Flutter UI.
  • Widget tree: the parent-child hierarchy of widgets that describes the UI.
